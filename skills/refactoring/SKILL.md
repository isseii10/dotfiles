# refactoring

リファクタリングは、**次の変更を楽にするために**、振る舞いを変えずに構造を変えること。目的は速さ（機能追加とバグ修正を速くする）で、見た目の美しさではない。"Make the change easy, then make the easy change."

作業中は **two hats** のどちらか一方だけをかぶる。refactoring の帽子では振る舞いを1文字も変えず、adding function の帽子では構造を変えない。

## 引数

対象（ファイル、関数、パッケージ）と、このあと何を変えたいか。変えたいことが書かれていなければ聞く。特になければ、最近よく変わっている場所（`git log`）を優先し、触る予定のない場所は散らかっていても計画に入れない。

## Step 1: 安全網を確かめる

テストを走らせ、全部通ることを確かめる。そのうえで、対象の振る舞いがテストで押さえられているかを確かめる。読むだけで済ませず、**壊して確かめる**：守りたい振る舞いを一時的に壊し、テストが落ちることを見てから戻す。落ちなければ、それはテストの穴。

穴があれば、今の振る舞いをそのまま固定するテスト（characterization test）を足すステップを Step 2 の計画の先頭に入れる。今の振る舞いがバグに見えても、そのまま固定してバグとして報告する。

完了条件：対象の振る舞いを壊すと落ちるテストがあり、全部通っている（または、それを作るステップが計画にある）。

## Step 2: 臭いを診断して計画を出す

[CATALOG.md](CATALOG.md) を読み、対象のコードの臭いを探す。Go のコードなら [GO.md](GO.md) も読む。臭いとリファクタリングは、CATALOG.md の英語名で書く。

計画には次を書く。

- **臭い**：場所（`file:line`）、**どう困るか**（次の変更で何が面倒になるか）、直したときの効き目。効き目が小さいなら小さいと書くか、計画から外す。
- **ステップの一覧**：1ステップ = 名前のあるリファクタリング1つ = 1コミット。各ステップに、リファクタリング名、対象、コミットメッセージ案を書く。呼び出し元は同じステップでまとめて直す。一度に直せない呼び出し元があるときだけ段階を踏む（CATALOG.md「呼び出し元の直し方」）。
- **振る舞いの変更の候補**：バグや仕様の疑問は、ステップとは別の一覧に分けて書く。
- **言語に合わない手順**：カタログの手順がその言語に合わないところは、そう書いて合わせ方を決める。

計画を出したら止まり、承認を待つ。直すように言われたら直して出し直す。

完了条件：ユーザーが計画を承認した。

## Step 3: 1ステップずつ実行する

承認された計画を上から順に、ステップごとに次の4つを行う。

1. 変える。LSP や IDE のリファクタリング機能（rename、inline）があれば使う。
2. 新旧が**同じ振る舞い**かを、テストが押さえていない境界まで確かめる。負の値、空、ゼロ値、`NaN`、`nil`、条件の短絡評価で呼ばれなくなる副作用、評価の順番。違いがあれば、テストを足すか、振る舞いの変更の候補に回す。
3. テストを走らせる。テストの期待値は変えない。
4. 差分を読み、次の3つを確かめる。そのステップの変更だけが入っている。意図した変更が実際に起きている（一括置換が何も変えずにテストだけ通ることがある）。古い道が残っていない（同じことをする古い関数、ゲッター、別名が残ると、やり方が2通りになる）。最後に `git status` で関係ない変更が混ざっていないか確かめ、そのステップだけをコミットする。

テストが落ちたら、そのステップで自分が入れた変更だけを戻し、もっと小さいステップに分けてやり直す。

計画の前提が崩れたとき（手順が合わない、計画にない臭いのほうが先に要る、振る舞いを変えないと進めない）は、そこで止まって報告し、計画を直す承認を得る。

完了条件：計画のすべてのステップがコミットされ、どのコミットでもテストが通る。

## Step 4: 報告する

- コミットの一覧
- 計画から外した臭いと、途中で見つけた臭い（次の候補）
- 振る舞いの変更の候補と、見つけたテストの穴
- その言語らしくない書き方で、残したもの
- モジュール単位の問題（関数や型を動かしても片付かないもの）は、`/improve-codebase-architecture` の候補として伝える

## コミット

リポジトリのコミット規約に従う。なければ Conventional Commits の `refactor(<scope>): ...` にする。`refactor` のコミットではテストの期待値を変えない。振る舞いの変更は、承認を得たうえで別の `feat` / `fix` のコミットにする。そうすると、履歴のどこで振る舞いが変わったかがすぐ分かる。
